ServerDesk 服务登录体验 · 设计方案
版本：草案 v0.1
范围：只讨论设计，不含实现。目标是在不接管凭据的前提下，把"这个服务现在要不要登录"变得可感知。
====================================================================


一、目标与非目标
--------------------------------------------------------------------
目标
  1. 用户一眼看出哪些服务需要重新登录，哪些可以直接用。
  2. 点击卡片直接落到该服务的登录页（或已登录后的主界面），不需要二次寻找入口。
  3. 会话过期时给一个明确、不打扰的提示，而不是让用户对着一堆报错猜。
  4. 保持"程序不持有任何服务凭据"这条边界不变。

非目标
  1. 不在应用内保存账号密码，不做自动填充。
  2. 不代理服务自身的认证逻辑（OAuth、验证码、2FA、单点登录）。
  3. 不做统一的账号体系，不同服务之间不共享登录态。


二、三条硬边界
--------------------------------------------------------------------
1. 凭据归服务。应用不读、不存、不转发用户名密码、Token、API Key。
2. 会话归 WebView2。登录态由各服务自己的 Cookie 维持，存在 WebView2 用户数据目录。
3. 判断只能是"推测"。对任意第三方 WebUI，没有通用的"是否已登录"信号；
   所有状态展示都必须允许被证伪，因此措辞不能是"已登录"，只能是"上次进入的是主界面"。

这三条决定了下面的方案：能做的只是"观察",不是"认证"。


三、登录状态怎么判定（核心问题）
--------------------------------------------------------------------
对任意后台，"是否已登录"没有标准答案。三种可选信号，按可靠性排序：

方案 A：不判定（最保守）
  卡片只显示在线/离线（现有 TCP 探测）。登录与否由页面自己表达。
  优点：零误报、零维护、零配置。
  缺点：用户点开前不知道要不要登录；会话过期时没有提示。

方案 B：URL 启发式（推荐作为默认）
  每个服务窗口记录"最后一次导航到的 URL"，匹配登录路径关键词：
    login / signin / sign-in / auth / #/auth / /oauth
  命中则视为"停在登录页"，否则视为"已进入主界面"。
  可行性：已确认 webview 的 url() 可读（顶栏现在每 2 秒轮询在用）。
  局限：
    - SPA 若登录后仍停留在 /login 路由，会误判（少见）。
    - 过期后只返回 401、URL 不变的 SPA，检测不到。
    - 拿不到页面标题（eval 无返回值，远程页面没有 IPC），只能靠 URL。
  成本：低（Rust 侧对每个服务窗口轮询一次 url，前端直接消费）。

方案 C：配置化探测（可选增强）
  每个服务可选填：
    authProbe: { path: "/api/status", loggedInStatus: 200, loginPath: "/login" }
  应用通过通道（或直连）发一个 GET，看状态码：
    200 -> 视为已登录；401/403/302 到登录页 -> 视为未登录。
  优点：唯一能发现"URL 不变但会话已失效"的手段。
  缺点：需要每个服务单独配置；探测请求会出现在服务日志里；
        带 CSRF/签名的接口不能用。
  成本：中（Rust 侧需要一个极简 HTTP 客户端，约 50 行，不引入新依赖）。

结论：默认走 B，提供 C 作为可选精确模式，A 作为"关掉提示"的开关。
状态永远标注为"推测"，并在设置里可关闭。


四、界面设计
--------------------------------------------------------------------
1) 首页服务卡片（三种视觉状态）

  在线 + 上次停在主界面
  ┌────────────────────────────────────┐
  │ [机器人图标] AstrBot          ● 在线 │
  │              AI · 6185              │
  │                                     │
  │  上次进入：主界面                    │
  │                          打开  →     │
  └────────────────────────────────────┘

  在线 + 上次停在登录页
  ┌────────────────────────────────────┐
  │ [机器人图标] AstrBot          ● 在线 │
  │              AI · 6185              │
  │                                     │
  │  上次进入：登录页                    │
  │                          去登录 →    │
  └────────────────────────────────────┘

  从未打开过（新增）
  ┌────────────────────────────────────┐
  │ [机器人图标] New API          ● 在线 │
  │              AI · 3001              │
  │                                     │
  │  尚未打开                            │
  │                          打开  →     │
  └────────────────────────────────────┘

  说明：措辞刻意用"上次进入：登录页/主界面"，而不是"未登录/已登录"。
  它陈述的是观察到的事实，不是对服务认证状态的断言。

2) 服务页顶栏（登录过程可见）

  停在登录页时，工具条右侧出现一个中性徽标：
    [‹][›][↻][⌂]  AstrBot  http://YOUR-SERVER:6185/#/auth/login   [ 等待登录 ]

  用户在该窗口完成登录后，URL 离开登录路径，徽标自动变为：
    [ 已进入工作区 ]

  不做弹窗，不做遮罩，不打断页面本身。

3) 侧边栏（不动）
  仅保留在线状态点与分组。登录状态只在卡片与顶栏出现，避免侧边栏信息过密。

4) 设置页 · 每个服务的登录项（可选区块）

  ┌ 登录识别 ──────────────────────────────┐
  │ 识别方式    [ 自动（按地址路径）   ▾ ]
  │             可选：自动 / 关闭 / 自定义探测
  │
  │ 探测地址     /api/status              （仅自定义时出现）
  │ 已登录状态码  200
  └───────────────────────────────────────┘

  默认"自动"，用户不需要理解任何东西；需要精确的服务手动开探测。


五、交互流程
--------------------------------------------------------------------
首次打开某服务
  卡片显示"尚未打开" -> 点击 -> 打开该服务首页 -> 若落在登录路径，顶栏出现"等待登录"。
  用户完成登录后，URL 变化 -> 顶栏变为"已进入工作区" -> 卡片状态同步为"上次进入：主界面"。

会话过期
  用户点开 -> 服务把页面跳到登录页 -> 顶栏"等待登录" + 卡片标记"上次进入：登录页"。
  不做任何账号相关的预填或提示，保持静默。

多标签/多窗口切换
  只有当前可见的服务窗口参与状态更新；隐藏窗口的状态在切回时刷新一次即可。

关闭到托盘再恢复
  恢复时重新轮询一次活动窗口的 URL，不依赖缓存，避免显示过期状态。


六、异常与边界情况
--------------------------------------------------------------------
1. 第三方 OAuth / SSO 跳转
   登录过程中跳到未配置的域名会被导航白名单拦下并交给系统浏览器（现有行为）。
   设计上明确：这类服务**无法在应用内完成登录**，卡片应允许标注"外部登录"，
   点击时直接打开系统浏览器，不做"等待登录"提示。
   （这是现有白名单策略的必然结果，需要如实告知，而不是假装能处理。）

2. 验证码 / 2FA
   应用不做任何干预，登录完全在页面内完成。

3. 登录后仍停留在 /login 路由的 SPA
   URL 启发式会持续显示"等待登录"。缓解：用户可在设置里把该服务改为"关闭识别"。

4. 过期后只返回 401、URL 不变的 SPA
   自动模式看不出来。只有配置化探测能发现。文档里要写清楚这个盲区。

5. 服务不可达
   沿用现有在线/离线状态，登录状态显示"未知"，不叠加两套红点。

6. 同一服务的多账号
   当前所有服务窗口共享一个 WebView2 数据目录，同一域名必然共享 Cookie，
   因此**不支持多账号**。要做需要"每服务独立数据目录"，代价是内存与启动时间上升。
   结论：暂不支持，并在设计里写明；如果确有多账号需求，单独立项。


七、安全设计
--------------------------------------------------------------------
1. 凭据
   不新增任何凭据存储。登录状态是观察结果，不是认证凭据。

2. 状态推断的隐私
   URL 轮询只在内存中进行，不落盘、不上传。落盘的只有设置（是否开启识别、探测路径）。

3. 本地锁（可选，默认关闭）
   目的：防止同机他人直接坐到已登录的面板前。
   推荐实现：Windows Hello（UserConsentVerifier），由系统校验生物特征或系统 PIN，
   应用不保存任何秘密。
   触发时机：启动、从托盘恢复、空闲 N 分钟、系统锁屏后恢复。
   明确局限：锁只挡界面，不加密 WebView2 的 Cookie。能读磁盘的攻击者依然可以拿到会话，
   它是"防顺手"而不是"防入侵"。

4. 退出登录
   V1.1 沿用"在服务页面里点退出"。应用不提供"一键注销所有服务"，
   因为不同服务的注销接口不同，硬做容易产生"看起来退了其实没退"的假象。


八、实现路径与成本
--------------------------------------------------------------------
项目                        改动位置                     成本   风险
URL 轮询与状态存储          windows.rs（每窗口 url 轮询）  小     误判（已在措辞上兜底）
卡片/顶栏状态 UI            HomeView / TopBar / store     小     无
"上次进入"持久化            config 增加每服务字段           小     配置字段迁移
设置页识别开关 + 探测配置   SettingsView + config          中     无
配置化 HTTP 探测            health.rs 复用 SOCKS 客户端    中     探测请求出现在服务日志
Windows Hello 本地锁        Rust + windows crate（WinRT）  中     需要处理无 Hello 设备的降级
多账号独立数据目录          windows.rs（data_directory）   中高   内存与启动开销

说明：配置化探测不引入新依赖——现有 health.rs 里已经有 SOCKS5 拨号能力，
补一个最小的 HTTP/1.1 请求读取状态行即可。


九、建议分期
--------------------------------------------------------------------
V1.1（建议先做，约 1 天）
  - URL 启发式识别（默认开）
  - 卡片三态 + 顶栏"等待登录/已进入工作区"
  - 设置页加"登录识别：自动/关闭"

V1.2（按需）
  - 配置化探测（解决 SPA 401 盲区）
  - 外部登录类服务的显式标注
  - Windows Hello 本地锁

暂不做
  - 凭据托管与自动填充
  - 一键注销所有服务
  - 多账号


十、需要你拍板的三件事
--------------------------------------------------------------------
1. 状态措辞
   建议用"上次进入：登录页/主界面"，而不是"未登录/已登录"。
   如果你希望更直白（"需要登录"），可以，但误判时会显得产品在说谎。选哪个？

2. 本地锁
   要不要做？如果做，我建议 Windows Hello 而不是自建 PIN（不存秘密、体验更好）。
   代价是首次使用多一次系统验证，且在没有 Hello 的机器上要降级到密码或直接关闭。

3. 外部登录类服务怎么处理
   有些服务（走 SSO 的后台）在应用内永远登不进去。是"点击时直接开系统浏览器"，
   还是"仍尝试在窗口里打开，失败后提示"？前者更诚实，后者更统一。
