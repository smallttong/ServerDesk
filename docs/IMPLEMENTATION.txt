服务器统一桌面控制中心（ServerDesk）
实现说明 · 供代码审查
版本 0.1.0 / 2026-10-31
====================================================================


一、范围与定位
--------------------------------------------------------------------
本程序是一个 Web 管理后台的聚合外壳，不实现任何服务器管理功能。
它只做四件事：

  1. 按本地配置加载并展示各服务原有的 WebUI（AstrBot、NapCat、1Panel、
     哪吒监控，以及用户自行添加的任意 http/https 地址）。
  2. 提供一个统一的 IDE 式壳：侧边栏、顶栏工具栏、首页、设置、托盘。
  3. 内置一条 Tailscale 组网通道，让上述页面在私网内可达。
  4. 做轻量的在线状态检测并持久化配置。

不包含：用户/权限系统、Docker/SSH/文件管理、云同步、插件市场、
自动服务发现、日志系统。这些按需求留作后续版本。

技术栈：
  Tauri 2（稳定 API）+ Rust + Vue 3 + Vite + TypeScript
  + Tailwind CSS 4 + Lucide 图标 + Go（tsnet sidecar）


二、运行形态与进程结构
--------------------------------------------------------------------
Windows 上共有两类进程：

  ServerDesk.exe        主进程（Rust + 系统 WebView2），一个进程内托管
                        主窗口与全部服务窗口
  serverdesk-channel.exe  组网通道 sidecar（Go），由主进程在启动时拉起

两者是父子进程关系，通过子进程的 stdout（每行一个 JSON）和 stdin（保活）
通信。主进程退出时 stdin 管道关闭，sidecar 侧读到 EOF 后自行退出；
主进程也保留 kill 作为兜底。

主进程内的窗口：
  main             壳窗口，加载内嵌前端（tauri://localhost），有完整 IPC 权限
  svc-<service-id> 服务窗口，加载远程 URL，无任何 IPC 权限

任何时刻只有一个服务窗口可见；窗口本身不销毁，只切换显示/隐藏，
因此登录态、滚动位置、WebSocket 连接在切换服务时都保留。

四、数据模型与配置文件
--------------------------------------------------------------------
位置：%APPDATA%\com.serverdesk.app\config.json
写入方式：先写 config.json.tmp，再 rename 覆盖，避免半写坏文件。
读取失败（JSON 损坏）时，把原文件备份为 config.json.bak，重建默认配置。

结构：
{
  "version": 1,
  "services": [
    {
      "id": "astrbot",           唯一，仅允许字母数字与 _ -，同时用于窗口 label
      "name": "AstrBot",
      "category": "AI",
      "url": "http://YOUR-SERVER:6185",
      "icon": "bot",             图标名，见 src/lib/icons.ts 的枚举
      "healthCheck": true,
      "sortOrder": 10,
      "enabled": true
    }
  ],
  "settings": {
    "autostart": false,
    "closeToTray": true,
    "startPage": "home",         home | last
    "channelEnabled": true,
    "channelHostname": "serverdesk",
    "channelTags": ""            例如 tag:serverdesk
  }
}

首启种子数据：AstrBot(6185)、NapCat(6099)、1Panel(10086)、哪吒监控(8008)，
地址均为 http://YOUR-SERVER:端口 的占位符，界面上显示"待配置地址"，
点开时会提示先改地址并跳到设置页。

Rust 侧校验（config::validate）：
  - id 非空、仅 ASCII 字母数字与 _ -
  - id 不重复
不通过则拒绝保存并把错误抛回前端。

注意：保存是全量覆盖语义，前端把整份配置发回 save_config，Rust 不认识的
字段在重写时会被丢弃（目前没有独立的迁移机制，靠 serde 默认值向后兼容）。

通道的节点身份不在配置里，位于
%APPDATA%\com.serverdesk.app\channel-state\（tsnet 自己维护的 state 目录）。
删除该目录或在界面点"退出登录"等同于注销该 tailnet 节点。


五、窗口模型（内嵌页面的实现）
--------------------------------------------------------------------
Tauri 2 稳定 API 不支持单窗口多 WebView，所以采用"主窗口 + 贴合的无边框
子窗口"方案。

1) 尺寸上报
   主窗口的 Vue 在挂载时、以及内容区尺寸变化时（ResizeObserver + window.resize），
   把内容区相对 webview 视口的 CSS 像素矩形上报给 Rust（命令 set_content_rect）。
   矩形由布局自然决定：左侧 240px 侧边栏、上方 56px 顶栏之外的部分。

2) 窗口创建（windows::open，async 命令）
   - 已存在的 svc-<id>：只做重新贴合 + show + focus，不重建。
   - 不存在时创建：
       decorations(false)、skip_taskbar(true)、resizable(false)、
       maximizable(false)、minimizable(false)、closable(true)、visible(false)、
       parent(主窗口)   —— 设为 owner，保证始终压在主窗口之上
       data_directory(%LOCALAPPDATA%\com.serverdesk.app\services-webview)
       proxy_url(socks5://127.0.0.1:PORT)   —— 仅当通道状态为 up
   - 创建后先按上报的矩形设 size/position，再 show，避免闪烁。
   - 切换服务时隐藏上一个窗口（不销毁）。

3) 坐标换算
   物理坐标 = 主窗口 inner_position（客户区左上角，物理像素）
              + 上报的 CSS 坐标 × 主窗口 scale_factor
   尺寸同理。set_size 先于 set_position，减少抖动。

4) 跟随
   主窗口的 Moved / Resized / ScaleFactorChanged 事件触发 sync_glue 重新贴合；
   前端 ResizeObserver 触发 set_content_rect 时，若当前有活动服务窗口也会立即重贴。

5) 为什么用独立 WebView2 数据目录
   WebView2 的 --proxy-server 是"每个环境"的参数，同一用户数据目录下的环境
   参数必须一致。主窗口不设代理，服务窗口要设代理，因此服务窗口单独用
   services-webview 目录，各自独立浏览器进程。

6) 通道就绪时的重建
   在通道从未就绪变为 up 的那一刻，之前创建的服务窗口其 WebView2 环境里
   没有代理参数，因此 Rust 会销毁全部 svc-* 窗口（windows::reset_service_windows），
   前端收到 channel-status 事件后重新打开当前服务。


六、内置组网通道（tsnet）
--------------------------------------------------------------------
设计目标：不装系统 VPN、不建虚拟网卡、不要管理员权限，程序自带一条到
tailnet 的管道。

结构：
  WebView2（服务窗口）── --proxy-server=socks5://127.0.0.1:PORT ──┐
                                                                  ├─ tsnet ─> tailnet
  健康检查（Rust 侧 SOCKS5 CONNECT）──────────────────────────────┘

1) sidecar（channel/main.go）
   启动参数：--state-dir、--hostname、--tags、--socks-addr（默认 127.0.0.1:0）、
             --authkey（保留，界面不暴露）
   流程：
     - 先绑定 SOCKS5 监听端口（随机端口），立即输出 {"event":"listening","port":N}，
       这样即使还没授权，端口也已确定，可以用于创建服务窗口。
     - 并发执行 srv.Up()（tsnet 的登录/连接流程）。
     - 每秒轮询 LocalClient().Status()，把状态与登录 URL 用 JSON 行输出：
         {"event":"status","backend":"Running|NeedsLogin|...","ip":"100.x.y.z"}
         {"event":"login","url":"https://login.tailscale.com/a/..."}
         {"event":"error","message":"..."}
     - stdin 读到 EOF 即退出（父进程消失时的保活手段）。

2) SOCKS5 服务端
   - 只实现无认证方法协商与 CONNECT 命令（浏览器访问 Web 只需要这个）。
   - 支持 ATYP=1/3/4（IPv4 / 域名 / IPv6），域名原样交给 tsnet 解析，
     所以 MagicDNS 名字可直接使用。
   - 节点未就绪时立即回 0x04（host unreachable）并输出 dial-error，
     避免每个请求都卡在 tsnet 的 dial 上直到超时。
   - 成功建立后双向 io.Copy；任一端关闭即结束。

3) Rust 侧（channel.rs）
   - ChannelStatus：phase(stopped/starting/login/up/error)、socksPort、loginUrl、
     ip、message、hostname、tags。
   - 用 std::process::Command 启动 sidecar，Windows 下加 CREATE_NO_WINDOW，
     stderr 丢弃（tsnet 的日志会刷屏），stdout 用独立线程逐行解析。
   - 状态变化通过 Tauri 事件 channel-status 推给前端；前端据此渲染侧边栏指示、
     设置页状态、首页横幅。
   - phase 变为 up 时触发 windows::reset_service_windows。
   - 停止：先关 stdin（让 sidecar 自行退出），再 kill 兜底。
   - 退出登录：停止进程、删除 state 目录、重新启动（会再次产出登录链接）。
   - 端口稳定性：sidecar 在授权前就绑定端口，且该监听不随登录状态变化，
     所以在一次运行期内端口固定；若 sidecar 重启导致端口变化，销毁旧窗口即可。

4) 配置联动
   save_config 时会对比 hostname 与 tags，变化则重启通道；关闭 channelEnabled
   则停止通道。
   健康检查与打开服务都要求通道就绪（channelEnabled 为假时则走直连）。


七、健康检查
--------------------------------------------------------------------
目的只是"这个服务在这个地址上是否可达"，不是 HTTP 语义检测。

  - 通道可用时：Rust 侧实现最小 SOCKS5 客户端（health::probe_via_socks），
    与页面走同一条路径，3 秒超时，按 SOCKS 应答码给出"连接被拒绝/主机不可达/通道未就绪"等。
  - 通道关闭时：直接 TcpStream::connect_timeout，1.8 秒超时。
  - 命令 check_services 是 async + spawn_blocking，每个服务一个线程并发探测。
  - 前端每 30 秒探测一次（页面隐藏时跳过），通道未就绪时清空结果，
    卡片状态回到"未知"而不是误报离线。

选择 TCP/L4 探测而不是 HTTP，是为了不受登录墙、重定向、自签证书、CORS 影响。
代价是：端口开着但应用挂掉时会误报在线，这是已知取舍。


八、前端交互与状态流转
--------------------------------------------------------------------
视图状态：home / settings / service（service 时 activeId 表示当前服务）。

关键流程：
  init()
    get_config -> config_path -> channel_status -> 首次健康检查 -> 30 秒轮询
  openService(id)
    1. 服务存在且 URL 合法（非占位符、http/https 开头）
    2. 通道就绪（channelEnabled 时要求 phase == up），否则 toast + 跳设置页
    3. 置 view=service、activeId、记录 last-service，nextTick 后 invoke open_service
  goHome / goSettings
    切视图并 hide_all_services（隐藏所有 svc 窗口）
  channel-status 事件
    up：若当前在服务页，重新 invoke open_service（配合后端的窗口重建）
    非 up：清空健康结果；若在服务页则退回首页
  save_config
    前端整份发送，后端落盘、刷新托盘菜单、按需启停通道
  服务 CRUD
    新增/编辑/删除/上下移动/启停都改内存状态后立即 persist；
    删除时同时销毁对应 svc 窗口

设置页新增"网络通道"分区：状态与详情、在浏览器中授权（直接打开 loginUrl）、
重启通道、退出登录（两步确认）、启用开关、节点名、设备标签。
侧边栏底部常驻一个通道状态行（颜色点 + 文案），点击进入设置。

首页在通道未就绪时显示琥珀色横幅并给出"去设置"入口。


九、安全边界
--------------------------------------------------------------------
1) IPC 权限
   capabilities/default.json 只把权限授予 main 窗口：
     permissions: core:default, opener:default
   服务窗口加载的是远程页面，不在能力绑定范围内，页面里的 JS 无法调用任何
   后端命令（Tauri 2 的 remote 权限默认关闭）。

2) 导航白名单
   每个服务窗口创建时挂 on_navigation：
     - 目标主机在"配置里出现过的 host + localhost/127.0.0.1/::1/0.0.0.0"内 -> 允许
     - about/data/blob -> 允许
     - 其他 -> 取消加载，并交给系统默认浏览器打开
   匹配的是主机名而不是完整 origin，因此同一台机器换端口/换 http、https 都放行；
   跳转到第三方域名（如外部 SSO）会落到系统浏览器。

3) 弹窗
   注入初始化脚本覆盖 window.open：http/https 目标改为当前窗口跳转（仍受上面的
   白名单约束），非 http(s) 交回原生实现。

4) 凭据
   程序不保存任何服务账号、密码、Token、API Key。登录态完全由各服务自己的
   Cookie/Session 维持，存在 WebView2 用户数据目录里。
   通道节点私钥存在 channel-state 目录，属于凭据级别，目前是普通文件
   （用户目录权限保护），未做 DPAPI 加密——这是一个可以改进的点。

5) 本地代理
   SOCKS5 端点不做认证，但只监听 127.0.0.1，外部不可达。
   CONNECT 只允许已启用服务的私网入口 host:port，其他目标返回规则拒绝。
   端口是随机分配的，不写配置文件。

6) 建议的 tailnet 收敛
   设置里可填 tag:serverdesk，配合 ACL 限制该节点只能访问指定端口。


十、构建与打包
--------------------------------------------------------------------
命令：
  npm install
  npm run tauri build

产物：
  src-tauri/target/release/server-desk.exe
  src-tauri/target/release/serverdesk-channel.exe
  src-tauri/target/release/bundle/nsis/ServerDesk_0.1.0_x64-setup.exe

两个必须注意的约束：

  1. 不要用 cargo build --release 直接构建。
     Tauri CLI 在构建时会注入内嵌前端所需的构建环境；直接用 cargo 构建出的
     程序会去连 http://localhost:1420（Vite 开发服务器）而不是内嵌资源，
     表现为打开就是"无法访问此页面"。

  2. sidecar 的命名必须带 target triple：
     src-tauri/binaries/serverdesk-channel-x86_64-pc-windows-msvc.exe
     tauri.conf.json 的 bundle.externalBin 写 binaries/serverdesk-channel；
     打包时会被复制为 serverdesk-channel.exe 放在主程序旁边。
     绿色版必须两个 exe 同目录，否则提示"找不到通道程序"。

  3. NSIS 打包依赖本地工具集：
     %LOCALAPPDATA%\tauri\NSIS\ 需要有 makensis.exe、Stubs、Include，
     以及 Plugins\x86-unicode\additional\nsis_tauri_utils.dll。
     首次打包时 Tauri 会从 GitHub 下载，网络受限时会卡住，可手动放置。

release profile：panic=abort、opt-level=s、lto=false、strip=true、codegen-units=4
（关掉 LTO 是为了让增量构建保持在 1 分钟左右）。


十一、已知限制与未验证项
--------------------------------------------------------------------
1. 没有真实 tailnet 的端到端验证。
   已验证：通道进程启动、未授权时的登录链接、状态机、SOCKS5 协议正确性、
   WebView2 通过 socks5 代理加载页面（含 WebSocket 与 Cookie）、主机名透传
   （用本机无法解析的 mock.tailnet.test 验证 MagicDNS 路径）。
   未验证：授权后真正访问 tailnet 内的服务器。需要在有账号的环境里补一次。

2. 托盘菜单的右键菜单没有用自动化点开过（图标折叠在 Windows 溢出区）。
   菜单构建与全部菜单项处理函数已实现，其中"打开控制中心"与单实例回调共用
   show_main，该路径已通过启动第二个实例间接验证。

3. 通道节点私钥未加密（见九.4）。

4. 只允许一个服务窗口可见，但所有打开过的服务窗口都常驻内存。服务数量很多时
   内存会累积，目前没有空闲回收。

5. 健康检查是 L4 可达性，不反映 HTTP 状态码。

6. 下载行为依赖 WebView2 默认策略，没有单独验证"点击下载 -> 保存到下载目录"。

7. window.open 被改写为同窗口跳转，依赖弹窗的 OAuth 流程行为会与浏览器不同。

8. 配置保存是全量覆盖且丢弃未知字段，没有独立迁移框架。

9. 服务页面若跳到未配置的主机（例如第三方登录页），会被拦下并丢到系统浏览器，
   这类流程在程序内无法完成。


十二、开发过程中修复的关键问题（供参考）
--------------------------------------------------------------------
1. 同步 Tauri 命令会阻塞主线程，而创建 WebView2 窗口需要主线程消息循环。
   症状：窗口被创建但永远不可见、几何设置全部无效、前端 invoke 永不返回。
   修复：open_service / close_service 改为 async 命令（见 lib.rs 注释）。

2. 关闭到托盘后重新唤起，服务窗口不会自动重现。
   修复：托盘与单实例共用 show_main，后者 emit main-shown，前端收到后重新
   invoke open_service。

3. 通道未授权时 SOCKS5 建连会挂满 20 秒。
   修复：sidecar 维护 connected 原子标志，未就绪直接回 SOCKS 0x04。


十三、建议的审查重点
--------------------------------------------------------------------
按优先级：

  A. channel/main.go 的 SOCKS5 服务端
     帧解析边界（长度、ATYP、掩码）、错误码、半关闭处理、并发连接下的资源释放。

  B. src-tauri/src/windows.rs
     贴合坐标换算（DPI、多显示器、窗口最大化）、on_navigation 白名单范围、
     初始化脚本注入、reset_service_windows 的时序。

  C. IPC 暴露面
     capabilities/default.json 是否确实只覆盖 main；
     确认服务窗口（远程页面）拿不到任何命令。

  D. src-tauri/src/config.rs
     校验充分性（id 字符集、重复）、原子写入、损坏配置的恢复路径。

  E. 状态机与错误路径
     channel.rs 的 phase 迁移是否有死角（例如进程崩溃、端口被占用）、
     大量 let _ = 忽略错误的地方是否该上报。

  F. 前端
     openService 的前置检查、通道事件与视图状态的一致性、
     配置保存失败时的用户可见反馈。
